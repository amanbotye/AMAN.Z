06.2 [قاعدة] العرض المحلي

• 06.2.1 قراءة البيانات المعروضة من الحالة المحلية.

• 06.2.2 لا يعاد تحميل الشاشة مع كل تنقل.

• 06.2.3 تحديث البيانات المحلية يؤدي إلى تحديث الواجهة تلقائيًا.

• 06.2.4 العودة إلى الشاشة تعرض آخر حالة محلية متزامنة.

06.3 [قاعدة] العمليات الحساسة

• 06.3.1 لا يتم تنفيذ العملية الحساسة اعتمادًا على الحالة المحلية فقط.

• 06.3.2 العملية ترسل إلى الخادم/RPC.

• 06.3.3 لا تظهر Success قبل النتيجة الحقيقية من الخادم.

• 06.3.4 بعد نجاح الخادم يتم تحديث الحالة المحلية.

• 06.3.5 عند الفشل لا يتم تسجيل نجاح وهمي.

06.4 [قاعدة] عدم الاتصال

• 06.4.1 عرض Offline.

• 06.4.2 منع العمليات التي تتطلب اتصالًا.

• 06.4.3 توضيح سبب تعطيل الإجراء.

• 06.4.4 السماح للمستخدم بمراجعة البيانات المحلية التي يمكن عرضها.

06.5 [قاعدة] منع التكرار

• 06.5.1 منع الضغط المتكرر أثناء التنفيذ.

• 06.5.2 إظهار Loading للإجراء.

• 06.5.3 عدم إنشاء عملية ثانية بسبب الضغط المكرر.

• 06.5.4 معالجة Duplicate/Conflict من الخادم.

08. [قواعد الحماية والتجديد]

08.1 [قاعدة] الحماية

• 08.1.1 حماية واحدة فعالة فقط لكل رقم.

• 08.1.2 الرقم يمكن أن يكون موجودًا لأكثر من عميل.

• 08.1.3 وجود الرقم في حساب العميل لا يعني أن الحماية فعالة.

08.2 [قاعدة] التجديد

• 08.2.1 التجديد متاح لمالك الحماية الفعالة.

• 08.2.2 يبدأ التجديد من تاريخ انتهاء الحماية الحالية.

• 08.2.4 طلب التجديد يخضع لنفس التحقق المطلوب.

• 08.2.5 تنفيذ التجديد يتم من خلال الإجراء المخصص.

• 09.3.2 يتحقق الخادم من صلاحية التنفيذ.

• 09.3.3 عند النجاح تسجل العملية.

• 09.3.4 يتم إنشاء المهمة التالية عند انطباق الإعداد.

09.4 [قاعدة] إعادة الجدولة

• 09.4.1 متاحة فقط إذا سمحت إعدادات الشركة.

• 09.4.2 حفظ التاريخ السابق.

• 09.4.3 حفظ التاريخ الجديد.

• 09.4.4 حفظ السبب.

• 09.4.5 تسجيل العملية.

09.5 [قاعدة] الإلغاء

• 09.5.1 لا يوجد زر إلغاء في شاشة تنفيذ المهمة الحالية.

• 09.5.2 عند وجود مسار إلغاء معتمد من النظام، يلزم سبب الإلغاء.

• 09.5.3 لا يتم حذف المهمة حذفًا نهائيًا.

10. حالات الإدارة العامة

تستخدم حسب الحاجة:

Normal

البيانات متاحة.

Loading

قراءة أو عملية جارية.

Empty

لا توجد بيانات.

Error

فشل العملية.

Retry

إعادة المحاولة.

Offline

لا يوجد اتصال.

Session Expired

انتهت جلسة المدير.

Unauthorized

لا يملك المستخدم صلاحية العملية.

Duplicate

العملية مكررة.

Conflict

تعارض مع حالة حالية في الخادم.

Success

نجاح مؤكد من الخادم.

11. منع الضغط المكرر

عند تنفيذ عملية حساسة:

ضغط الزر → Loading → Disable Action → Server → Result → Enable Action 

ولا يسمح بإرسال نفس العملية مرتين بسبب الضغط المتكرر.

12. قاعدة الإلغاء والحذف

لا يتم استخدام الحذف الصامت للبيانات التاريخية الحساسة.

بالنسبة للعمليات التي تتطلب حالة إلغاء:

Cancel → Required Reason → Server → Audit → Status Update 

ولا يتم حذف السجل التاريخي.

وبالنسبة للمهمة تحديداً، لا يظهر زر إلغاء ما لم تكن القاعدة التشغيلية المعتمدة تسمح به.

13. سجل العمليات Audit

كل عملية إدارية حساسة تسجل:

من قام بالعملية → نوع العملية → الكيان المستهدف → الحالة السابقة → الحالة الجديدة → وقت العملية → البيانات اللازمة للتتبع 

السجل تاريخي وغير قابل للتعديل من الواجهة.

14. المزامنة

المسار الأساسي:

Server ↓ Sync ↓ Local DB ↓ State ↓ UI 

ولا تعتمد الواجهة على إعادة طلب البيانات من الخادم عند كل انتقال بين التبويبات.

18. نتيجة الطبقة الثانية

بعد تنفيذ هذه المصفوفة يصبح لدينا:

الطبقة الأولى الشجرة التنفيذية ↓ الطبقة الثانية مصفوفة التنفيذ ↓ كل شاشة → كل تبويب → كل نافذة → كل قسم → كل عنصر → مصدر البيانات → نوع العملية → الاتصال → الحالة → التحديث → قواعد التنفيذ 

وبذلك تكون الطبقة الثانية مرجعاً تنفيذياً للعميل والإدارة، وليست طبقة تصميم مستقلة ولا تضيف شاشات أو وظائف خارج الشجرة المعتمدة.

00. مبدأ بيانات الإدارة

واجهة الإدارة لا تمتلك قاعدة بيانات مستقلة عن النظام.

هي واجهة تشغيل وإدارة للبيانات المركزية نفسها.

Admin UI ↓ Admin State ↓ Local DB / Cache ↓ Repository / Sync ↓ Backend ↓ PostgreSQL

28. قواعد Snapshot للإدارة

الإدارة تستطيع تغيير الإعداد الحالي:

Package Price Task Interval Payment Method Provider Name 

لكن لا يجب أن تتغير البيانات التاريخية.

مثال:

Package السعر الحالي = 1000 

تم إنشاء طلب:

package_price_snapshot = 1000 

ثم غير المدير السعر إلى:

1500 

يبقى الطلب التاريخي:

1000 

ولا يعاد حسابه من جدول الباقات.

29. قاعدة قبول طلب الحماية

البيانات اللازمة للعملية:

protection_request payment_transaction customer customer_number phone_number provider package payment_method 

قبل القبول:

الطلب Pending + المستخدم صحيح + الرقم صحيح + الطلب غير متعارض + الدفع متحقق + الباقة صحيحة + الشركة صحيحة + لا توجد حماية فعالة متعارضة 

ثم:

Approve → Protection → Initial Task Plan → Financial Record → Client Notification → Audit 

وكل ذلك داخل عملية موثوقة واحدة قدر الإمكان.

30. قاعدة قبول التجديد

Renewal Request + Active Protection + Owner Match + Payment Verified + No conflicting renewal 

ثم:

Approve Renewal → Extend Protection → Preserve History → Recalculate Future Tasks → Financial Record → Client Notification → Audit 

31. قاعدة تغيير فاصل المهام

repeat_interval_days

ولا يتم تعديل التاريخ السابق للمهمات المكتملة.

32. قاعدة ظهور المهمة

36. قواعد INSERT للإدارة

لا يسمح بالتعديل الحر على العمليات الحساسة.

إعدادات النظام

يمكن إدارتها عبر عمليات موثوقة.

البيانات التشغيلية

مثل:

Approve Request Complete Task Reschedule Task Approve Renewal 

تنفذ بواسطة Trusted RPC/Transaction.

37. قواعد UPDATE للإدارة

التعديل المباشر على الجدول ليس بديلاً عن قواعد العمل.

مثلاً لا يسمح للواجهة أن تنفذ:

UPDATE protections SET end_at = ... 

بشكل حر.

بل:

Approve Renewal → RPC → Validate → Transaction → Update → Audit 

38. قواعد DELETE للإدارة

الحذف الفيزيائي ليس مساراً تشغيلياً عادياً.

يستخدم:

Disable Deactivate Reject Expire Void History 

بحسب الكيان.

39. قاعدة التزامن

عند وصول تغيير من الخادم:

Server ↓ Sync ↓ Local DB ↓ State ↓ UI 

مثال:

عدد العملاء = 21 

ثم تسجيل عميل جديد:

Server → Customer #22 → Sync → Local DB → Dashboard = 22 

ولا يحتاج المدير إلى:

Logout Login 

ولا إلى إعادة تحميل التطبيق كاملاً.

40. قاعدة Conflict

إذا نفذ المدير عملية على سجل تغير في الخادم:

Local State ≠ Server State 

فلا تنفذ العملية على البيانات القديمة.

يظهر:

Conflict → Refresh/Synchronize → إعادة قراءة الحالة → السماح بإعادة العملية إذا بقيت مسموحة 

41. قاعدة Duplicate

كل عملية حساسة يجب أن تكون قابلة للحماية من التكرار.

مثال:

ضغط قبول مرتين 

لا ينتج:

Protection A Protection B 

بل عملية واحدة ناجحة، والثانية:

Duplicate / Conflict 

42. قاعدة الأمن النهائية

UI ≠ Authority 

و:

Local DB ≠ Authority 

والسلطة الفعلية للعمليات الحساسة هي:

Backend + Database Constraints + Trusted RPC + Transaction + Authorization + Audit

• الطلب موجود.

• الطلب ما زال Pending.

• العميل موجود.

• الرقم موجود.

• الرقم مرتبط بالعميل.

• الباقة موجودة.

• وسيلة الدفع موجودة.

• إثبات الدفع صالح وفق القاعدة.

• لا توجد حماية فعالة متعارضة.

62. Audit ليس نجاح العملية

لا يكفي أن يتم إنشاء Audit فقط.

العملية الأساسية يجب أن تنجح أولاً.

مثال:

لا يجوز:

على أنه قبول مكتمل.

يجب أن تعكس سجلات التدقيق العملية الحقيقية.

63. العمليات الإدارية الحساسة

Add Number Approve Protection Request Approve Renewal Change Task Interval Create Protection Request Create Renewal Execute Task 

وفي واجهة الإدارة تحديداً:

Approve Request Reject Request Execute Task Reschedule Task Approve Renewal Reject Renewal Change Interval Change Task Amount Change Package Change Company Change System Settings 

كل عملية منها تمر عبر المسار الموثوق المناسب.

64. العمليات التي يجب ألا تنفذها الشاشة مباشرة

لا تنفذ الشاشة مباشرة:

INSERT protection UPDATE protection.end_at UPDATE request.status INSERT financial_transaction UPDATE task.status 

بدلاً من ذلك:

UI ↓ Use Case ↓ Repository ↓ Trusted RPC ↓ Database Transaction

66. Offline في الإدارة

يمكن للإدارة Offline:

• فتح الشاشات.

• قراءة البيانات المخزنة.

• البحث.

• التصفية.

• مشاهدة آخر حالة متزامنة.

• فتح التفاصيل الموجودة محلياً.

67. العمليات الممنوعة Offline للإدارة

لا تنفذ Offline:

• قبول طلب.

• رفض طلب.

• تنفيذ مهمة.

• إعادة جدولة مهمة.

• قبول تجديد.

• رفض تجديد.

• تغيير إعدادات الشركة الحساسة.

• تغيير الباقة.

• تغيير وسيلة الدفع.

• تغيير إعدادات النظام.

• أي عملية مالية.

• أي عملية تغير حالة الخادم.

68. قاعدة عدم النجاح الوهمي

مثال:

Manager taps Approve 

لا يظهر:

Approved 

إلا بعد:

RPC Success + Transaction Commit 

ثم:

Local Update 

69. Conflict

مثال:

Manager opens Request 

ويظهر محلياً:

pending 

لكن مديراً آخر أو عملية أخرى غيرت الحالة.

عند الضغط:

RPC ↓ Current State Check ↓ Conflict 

ثم:

Refresh/Sync ↓ Current State 

ولا يتم تنفيذ العملية على الحالة القديمة.

70. Duplicate

مثال:

Approve Approve 

أثناء تنفيذ الأولى:

Button Disabled 

وعلى الخادم:

Idempotency / State Constraint 

فتكون النتيجة عملية واحدة فقط.

71. Session Expired

إذا انتهت جلسة المدير:

72. Unauthorized

إذا لم يعد الحساب إدارياً:

Unauthorized

73. Forbidden

إذا كانت الجلسة صحيحة لكن العملية غير مسموحة:

ولا يحاول التطبيق الالتفاف على الصلاحية.

74. Not Found

إذا فتح المدير سجلاً لم يعد موجوداً أو لم يعد متاحاً:

ثم:
