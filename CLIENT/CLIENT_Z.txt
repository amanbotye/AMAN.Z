07. قواعد الاتصال

القراءة

فتح الشاشة → قراءة Local DB → عرض البيانات فوراً → مزامنة عند الحاجة → تحديث Local DB → تحديث UI 

العملية الحساسة

ضغط الزر → Validation → Connection Check → Server/RPC → التحقق الحقيقي → نجاح الخادم → تحديث Local DB → تحديث UI 

عند عدم الاتصال

Offline → عرض البيانات المحلية → السماح بالتصفح → منع العمليات التي تتطلب Server → إظهار Connection Required 

منع النجاح الوهمي

لا توجد:

ضغط → حفظ محلي → Success 

بل:

ضغط → Server → Success حقيقي → Local Update → UI Update

• البيانات التي يستطيع العميل إنشاؤها عبر العمليات الموثوقة.

• البيانات التي لا يملك العميل تعديلها مباشرة.

• البيانات التي تحفظ محلياً.

• البيانات التي تأتي من الخادم.

• البيانات التي تحتاج مزامنة.

• قواعد عدم الحذف.

• قواعد عدم التكرار.

• قواعد الملكية.

• قواعد العزل بين العملاء.

10. قواعد التكرار للطلبات

طلب حماية جديد

يمكن وجود أكثر من طلب حماية Pending لنفس الرقم وفق قواعد النظام، ولا يمنع تطبيق العميل إنشاء الطلب لمجرد وجود طلب Pending آخر لنفس الرقم. وحسم التعارض يكون عند القبول الذري في الخادم: أول قبول صحيح يفوز (First valid atomic acceptance wins) والطلبات المتعارضة الأخرى ترفض/تغلق وفق قاعدة التعارض المعتمدة (Conflict).

طلب تجديد

لا يسمح بوجود أكثر من طلب تجديد Pending للحماية نفسها.

الهدف

منع:

طلب A Pending طلب B Pending لنفس عملية الحماية 

من دون قاعدة واضحة.

14. التجديد

لا يحتاج التجديد إلى كيان مستقل إذا كان نموذج النظام المعتمد يستخدم:

protection_requests 

مع:

request_type = renewal previous_protection_id 

وبذلك يكون:

Protection Request │ ├── new_protection │ └── renewal 

قاعدة التجديد

الحماية الحالية → طلب تجديد → الدفع الخارجي → مرجع التحويل → Pending → مراجعة → Approved → تمديد الحماية 

قاعدة التاريخ

إذا كانت الحماية تنتهي بعد 10 أيام وتمت الموافقة على 365 يوماً:

تاريخ الانتهاء الجديد = تاريخ الانتهاء الحالي + 365 يوم 

وليس:

تاريخ الموافقة + 365 يوم

23. قواعد ملكية العميل

customer_id = auth.uid() 

أو علاقة مباشرة موثوقة إلى حسابه.

• عميل آخر.

• رقم مرتبط بعميل آخر إلا إذا كان النظام يسمح بعرض الكيان العام دون كشف بيانات صاحبه.

• سجل مالي إداري.

• سجل العمليات.

• إعدادات الشركات الداخلية.

• إعدادات المهام الداخلية.

• بيانات الإدارة.

• إعدادات التطبيق المحلية.

• حالة الحماية.

• السعر.

• تاريخ الانتهاء.

فلا تعدل مباشرة من العميل.

26. قواعد DELETE للعميل

لا يوجد حذف فعلي للبيانات التشغيلية الحساسة.

• protection.

• protection request.

• payment transaction.

• task.

• financial transaction.

• audit log.

27. البيانات المشتقة

لا تخزن كحالة مستقلة إذا كان يمكن حسابها بأمان.

end_at - current_time

due_at < current_time AND status != completed

مشتقة من تاريخ due_at.

الطبقة الرابعة — منطق التشغيل والربط الكامل لتطبيق العميل

المرجع النهائي لمنطق التطبيق، مصادر البيانات، العمليات، الحالات، الاتصال، المزامنة، والخادم

00. وظيفة الطبقة الرابعة

الطبقة الرابعة تحدد كيف يتحول ما تم تعريفه في:

• الطبقة الأولى: الشجرة التنفيذية.

• الطبقة الثانية: مصفوفة التنفيذ.

• الطبقة الثالثة: نموذج البيانات.

إلى تطبيق يعمل فعلياً.

وتحدد بالتحديد:

• مصدر البيانات لكل شاشة.

• متى يقرأ التطبيق من Local DB.

• متى يقرأ من الخادم.

• متى يسمح بالعمل Offline.

• متى يمنع العملية Offline.

• كيف تنتقل العملية من UI إلى ViewModel.

• كيف تنتقل إلى Repository.

• كيف تصل إلى Backend/RPC.

• كيف تعود النتيجة.

• متى تحدث Local DB.

• متى تحدث الواجهة.

• كيف تمنع العمليات المكررة.

• كيف تعالج Conflict.

• كيف تعالج Session Expired.

• كيف تعالج Unauthorized وForbidden.

• كيف تتعامل مع Loading / Empty / Error.

• كيف تتم مزامنة البيانات.

• كيف تحفظ الحالة بعد نجاح العملية.

• كيف تمنع ظهور نجاح وهمي.

01. المعمارية التشغيلية العامة

البنية الأساسية:

UI ↓ ViewModel / State Holder ↓ Use Case / Application Operation ↓ Repository ↓ Local DB / Remote Backend ↓ Server RPC / Database ↓ Result ↓ Repository ↓ Local DB ↓ State ↓ UI 

ولا يكون المسار:

UI ↓ SQL 

ولا:

UI ↓ Supabase Table مباشرة 

في العمليات الحساسة.

02. مصدر الحقيقة

02.1 البيانات المعروضة

البيانات الموجودة بالفعل في التطبيق يمكن عرضها من:

Local DB 

حتى لا يعتمد فتح كل شاشة على اتصال مستمر.

02.2 البيانات الحساسة

العمليات التي تغير حالة النظام مصدر الحقيقة فيها:

Backend 

وليس:

Local DB 

02.3 القاعدة النهائية

Local DB = Cache + Read State 

بينما:

Backend = Authority 

03. تشغيل التطبيق

03.1 بدء التشغيل

التسلسل:

App Start ↓ Initialize App ↓ Initialize Local DB ↓ Initialize Secure Session ↓ Restore Session 

04. استعادة الجلسة

الحالات

Restoring Authenticated Customer No Session Invalid Session Suspended Disabled Initialization Error 

إذا كانت الجلسة صحيحة:

Auth ↓ Load User Profile ↓ Check user_type ↓ Customer ↓ Customer Home 

إذا لم توجد جلسة:

Login 

إذا انتهت أو أصبحت غير صالحة:

Clear Invalid Session ↓ Login 

لا يتم عرض بيانات المستخدم السابقة كأنها جلسة صالحة.

05. تحميل ملف العميل

بعد نجاح المصادقة:

Auth User ↓ users ↓ Validate status ↓ Load customer state ↓ Load local synchronized data ↓ Route Customer 

إذا كان:

status = suspended 

لا يدخل العميل إلى الواجهة التشغيلية.

إذا كان:

status = disabled 

لا يدخل العميل إلى الواجهة التشغيلية.

06. مبدأ تحميل الشاشات

الشاشات ثابتة في التطبيق.

لا يتم:

فتح الشاشة → تنزيل كود الشاشة 

ولا:

كل ضغط → إعادة تحميل التطبيق 

بل:

Screen ↓ Observe State ↓ Read Local DB ↓ Render 

وعند وجود تحديث:

Local DB changed ↓ Reactive State ↓ UI updates 

07. الشاشة الرئيسية

07.1 قراءة البيانات

الرئيسية لا تنشئ إحصاءات من عندها.

تقرأ من Local DB:

• حالة الاشتراك/الحماية حسب البيانات المتاحة.

• عدد الأرقام.

• الحمايات الفعالة.

• طلبات الحماية الحالية.

• آخر الإشعارات.

• البيانات الزمنية المتعلقة بالحماية.

07.2 التحديث

Dashboard Open ↓ Observe Local DB ↓ Render 

إذا حدثت مزامنة:

Server Update ↓ Local DB Update ↓ Dashboard State Update ↓ UI Update 

لا يحتاج المستخدم إلى إعادة فتح الحساب.

08. حالة الرئيسية

Loading Loaded Partial Data Empty Offline Session Expired Error 

قاعدة Partial Data

إذا كانت بعض البيانات متاحة محلياً وبعضها غير متاح:

اعرض البيانات المتوفرة + وضح البيانات غير المتاحة 

ولا يتم اختراع قيم.

09. شاشة أرقامي

09.1 مصدر البيانات

Local DB ↓ customer_numbers ↓ phone_numbers ↓ protections 

09.2 التصنيف

الأرقام تقسم إلى:

مفعل للحماية غير مفعل للحماية 

التصنيف مشتق من حالة الحماية، وليس من قيمة يكتبها المستخدم يدوياً.

10. فتح تفاصيل الرقم

المسار:

Numbers ↓ Select Number ↓ Load Local Details ↓ Number Details 

إذا كانت البيانات المحلية غير موجودة أو قديمة:

Attempt Sync 

إذا كان الاتصال غير متاح:

Offline 

ولا تظهر بيانات غير معروفة على أنها مؤكدة.

11. إضافة رقم

هذه عملية حساسة ولا تعتبر ناجحة بمجرد إدخال الرقم.

المسار الكامل

Customer ↓ Add Number ↓ Enter Number ↓ Validate Format ↓ Normalize Number ↓ Detect Provider ↓ Check Prefix ↓ Check Length ↓ Check Valid Number ↓ Check Duplicate For Same Customer ↓ Server Trusted Operation ↓ Create customer_number ↓ Return Result ↓ Update Local DB ↓ Update UI 

12. التحقق من الرقم

12.1 التحقق المحلي

يمكن تنفيذ:

• تنظيف المسافات.

• التحقق من الشكل.

• التحقق من طول الرقم.

• التطبيع.

12.2 اكتشاف الشركة

التسلسل:

Normalized Number ↓ Provider Prefixes ↓ Provider Found 

إذا لم توجد البادئة:

Unsupported Prefix 

ولا يسمح للعميل باختيار الشركة يدوياً إذا كان النظام يستطيع تحديدها من البادئة.

13. حالة إضافة الرقم

Idle Validating Detecting Company Saving Success Invalid Prefix Invalid Length Invalid Number Duplicate For Same Customer Offline Conflict Server Error 

14. قاعدة نجاح إضافة الرقم

لا تظهر:

تمت إضافة الرقم 

إلا إذا:

Backend Success 

ثم:

Local DB Update Success 

ثم:

UI Update 

إذا فشل الخادم:

لا يتم تسجيل الرقم محلياً كرقم مضاف نهائياً. 

15. حالة الرقم الموجود مسبقاً

إذا كان الرقم موجوداً عند نفس العميل:

Duplicate For Same Customer 

ولا ينشأ سجل ثانٍ.

إذا كان الرقم موجوداً عند عميل آخر:

وجوده عند عميل آخر لا يعني تلقائياً رفض إضافته عند العميل الحالي؛ القرار النهائي يتبع قواعد ملكية الرقم المعتمدة في النظام، ولا يغير مجرد وجود سجل عميل آخر حالة الحماية.

16. طلب الحماية

المسار:

Number ↓ Request Protection ↓ Validate Number ↓ Check Customer Ownership ↓ Check Existing Active Protection ↓ Check Existing Conflicting Request ↓ Load Provider ↓ Load Available Package ↓ Load Payment Methods ↓ Prepare Request ↓ Enter Payment Reference ↓ Validate ↓ Submit ↓ Trusted RPC ↓ Pending Request ↓ Update Local DB ↓ UI 

17. الباقة في V1

نموذج البيانات يدعم الباقات.

لكن إذا كانت خدمة V1 الحالية تعتمد باقة الخدمة المعتمدة الوحيدة:

1000 YER 365 days 1 number 

فلا يتم اختراع خيارات متعددة للعميل في الواجهة.

يظل:

packages 

كياناً قابلاً للتوسع مستقبلاً.

18. اختيار وسيلة الدفع

يعرض العميل:

Active Payment Methods 

فقط.

مصدر البيانات:

Local DB 

مع المزامنة من الخادم.

العميل لا يعدل:

• اسم المستلم.

• رقم الحساب.

• تعليمات الدفع.

• حالة الوسيلة.

19. إدخال مرجع التحويل

العميل:

Enter Reference ↓ Validate ↓ Submit 

المرجع جزء من إثبات الدفع.

لا يعني إدخاله أن الدفع أصبح مقبولاً.

20. إنشاء طلب الحماية

عملية الإنشاء:

UI ↓ ViewModel ↓ CreateProtectionRequest Use Case ↓ Repository ↓ rpc_create_protection_request ↓ Database Validation ↓ Create Pending Request ↓ Return Request 

الدالة الموثوقة تنفذ التحقق النهائي.

21. ماذا يتحقق الخادم؟

على الأقل:

• المستخدم مصادق.

• المستخدم عميل.

• الرقم مرتبط بالعميل.

• الرقم صالح.

• الشركة صحيحة.

• الباقة متاحة.

• وسيلة الدفع متاحة.

• المرجع موجود حسب القاعدة.

• لا يوجد تعارض حماية.

• يمكن إنشاء الطلب بحالة Pending حتى لو وُجد طلب معلق آخر للرقم، وحسم التعارض يتم عند القبول الذري.

• حالة الرقم تسمح بالطلب.

22. نجاح طلب الحماية

إذا نجحت العملية:

protection_request.status = pending

Server Result ↓ Local DB ↓ Request Appears ↓ Home Updated ↓ Notifications Updated 

23. فشل طلب الحماية

إذا فشل:

Invalid Data Package Unavailable Payment Method Unavailable Protection Conflict Duplicate Request Unauthorized Forbidden Offline Server Error 

24. حالة إنشاء طلب الحماية

Select Number Loading Company Select Package Loading Package Select Payment Method Loading Payment Details Enter Transfer Reference Validating Submitting Success → Pending Review Invalid Data Package Unavailable Payment Method Unavailable Protection Conflict Duplicate Request Offline Server Error 

25. طلبات الحماية

العميل يقرأ:

Own Protection Requests 

فقط.

لا يقرأ طلبات العملاء الآخرين.

26. حالة طلب الحماية

27. تحديث طلب الحماية

مباشرة.

28. ظهور نتيجة القبول

إذا أصبح الطلب:

approved 

بعد المزامنة:

Request ↓ Protection ↓ Tasks / Plan ↓ Notification 

ولا تظهر الحماية على أنها فعالة قبل أن يصل تأكيد الخادم.

29. قاعدة الحماية الفعالة

حالة:

مفعل للحماية 

لا تعتمد على زر محلي.

بل على:

Server Protection + Active Status + Valid Dates 

30. الإشعارات

الإشعارات تأتي من أحداث النظام.

أمثلة:

request_submitted request_approved request_rejected protection_started protection_expiring protection_expired renewal_submitted renewal_approved renewal_rejected 

31. مسار الإشعار

Backend Event ↓ Create Notification ↓ Sync ↓ Local DB ↓ Notifications State ↓ UI 

ولا يستطيع العميل إنشاء إشعار لنفسه لتغيير حالة النظام.

32. قراءة الإشعار

عملية القراءة:

Open Notification ↓ Read Local State ↓ Mark Read ↓ Persist Read State 

إذا كانت القراءة تحتاج خادماً وفق التنفيذ النهائي:

UI ↓ Trusted/Authorized Update ↓ Server ↓ Local DB 

ولا يغير ذلك محتوى الإشعار.

33. التجديد

التجديد عملية حساسة.

المسار:

Active Protection ↓ Renew ↓ Verify Current Protection ↓ Verify Customer Ownership ↓ Load Eligible Package ↓ Load Payment Method ↓ Enter Reference ↓ Validate ↓ Create Renewal Request ↓ Server ↓ Pending ↓ Local Update 

34. قاعدة مالك التجديد

لا يستطيع العميل إنشاء تجديد لحماية لا تخصه.

التحقق:

auth.uid() = protection.customer_id 

والحماية يجب أن تكون:

active 

35. قاعدة تاريخ التجديد

إذا كانت الحماية الحالية:

end_at = اليوم + 10 أيام 

والتجديد 365 يوماً:

new_end_at = old_end_at + 365 days 

وليس:

current_date + 365 

36. قبول التجديد

العميل لا ينفذ القبول.

المسار:

Customer → Create Renewal Request → Pending → Manager Review → Approved → Backend Extends Protection → Sync → Customer sees new end date 

37. رفض التجديد

إذا رفض المدير:

renewal.status = rejected 

ثم:

rejection_reason 

ويصل للعميل بعد المزامنة/الإشعار.

الحماية الحالية لا تمدد.

38. حالة إنشاء التجديد

Idle Validating Submitting Success → Pending Duplicate Protection Not Active Not Owner Package Unavailable Payment Method Unavailable Offline Conflict Error 

39. منع التجديد المكرر

إذا كان هناك طلب تجديد Pending لنفس الحماية ولا تسمح القاعدة بإنشاء آخر:

Duplicate 

ولا ينشأ طلب ثانٍ.

40. الصفحة الرئيسية بعد تغير البيانات

مثال:

الحماية: منتهية 

ثم تمت الموافقة على التجديد:

Server ↓ Protection Updated ↓ Sync ↓ Local DB ↓ Home State ↓ Active Protection 

ويظهر التاريخ الجديد دون تسجيل خروج.

41. إعدادات العميل

الإعدادات التي لا تتطلب تغييراً حساساً في الخادم يمكن أن تكون محلية.

مثل:

• تفضيلات التطبيق.

• إعدادات العرض.

• قفل التطبيق.

• Biometric.

• اللغة إذا كانت ضمن اللغات المعتمدة.

أما بيانات الحساب التي يحكمها الخادم:

Server 

42. تغيير كلمة المرور

المسار:

Settings ↓ Change Password ↓ Validate Current Session ↓ Validate New Password ↓ Auth Provider ↓ Success ↓ Update Session State 

لا تخزن كلمة المرور في Local DB.

43. استعادة كلمة المرور

Forgot Password ↓ Enter Account Identifier ↓ Auth Recovery ↓ Recovery Result ↓ New Password 

ولا يحفظ التطبيق كلمة المرور القديمة.

44. تسجيل الخروج

Logout ↓ Confirm ↓ Sign Out ↓ Clear Session ↓ Clear Sensitive Local State ↓ Login 

لا يعني تسجيل الخروج حذف بيانات الخادم.

45. Offline Mode

التطبيق يجب أن يظل قابلاً للتصفح عندما لا يوجد اتصال.

يسمح Offline بـ:

• فتح الواجهة.

• قراءة البيانات المحلية.

• البحث في البيانات المحلية.

• التصفية.

• قراءة تفاصيل البيانات المتزامنة.

• قراءة الإشعارات المحلية.

• قراءة آخر حالة معروفة.

46. العمليات الممنوعة Offline

لا تنفذ Offline:

• إضافة رقم كعملية نهائية.

• إنشاء طلب حماية.

• إنشاء طلب تجديد.

• تغيير كلمة المرور إذا احتاج اتصالاً.

• أي عملية تغير حالة الخادم.

• أي عملية مالية.

• أي عملية حماية.

47. قاعدة Offline

عند الضغط على عملية حساسة بدون اتصال:

Offline / Connection Required 

ولا:

Success 

ولا:

تمت العملية 

ولا:

تسجيل محلي ينتظر التنفيذ 

إلا إذا تم تصميم Queue موثقة للعملية مستقبلاً. لا يتم اختراع Queue في V1.

48. المزامنة

المزامنة:

Authenticate ↓ Request Changes / Data ↓ Validate Ownership ↓ Merge/Replace According To Entity Rules ↓ Update Local DB ↓ Notify State 

49. أولوية الخادم

إذا اختلف:

Local 

مع:

Server 

في بيانات تشغيلية:

Server Wins 

ثم:

Local DB updated 

50. Conflict

إذا حاول العميل تنفيذ عملية على حالة لم تعد صالحة:

مثلاً:

Local: Protection inactive 

بينما الخادم:

Protection active 

فإن العملية لا تعتمد على Local State.

يرسل الطلب إلى الخادم، والخادم يرفض/يقبل وفق الحالة الحقيقية.

عند التعارض:

Conflict ↓ Refresh ↓ Sync ↓ Display Current State 

51. Duplicate

كل عملية حساسة يجب أن تمنع الضغط المزدوج.

مثال:

Submit ↓ Submitting 

زر الإرسال يصبح غير قابل للتكرار حتى وصول النتيجة.

وعلى الخادم يجب أن توجد حماية إضافية من التكرار.

52. Session Expired أثناء العملية

إذا انتهت الجلسة:

API/RPC ↓ Session Expired ↓ Stop Current Operation ↓ Do Not Show Success ↓ Clear Invalid Session ↓ Login 

ولا تحفظ العملية كنجاح محلي.

53. Unauthorized

إذا كان الحساب غير مصرح له:

Unauthorized 

لا يتم تجاوز الخطأ من التطبيق.

54. Forbidden

إذا كانت الجلسة صحيحة لكن العملية غير مسموحة:

Forbidden 

ولا يكرر التطبيق العملية تلقائياً.

55. Server Error

إذا حدث خطأ خادم:

Server Error 

ويحتفظ التطبيق بالحالة السابقة الصحيحة.

لا يحول:

Failed 

إلى:

Success 

56. Loading

كل عملية شبكية لها حالة:

Loading 

والعمليات الحساسة:

Button Disabled 

أثناء التنفيذ لمنع التكرار.

57. Error Recovery

بعد الخطأ:

Error ↓ Retry 

ولا يعاد تنفيذ العملية تلقائياً إذا كان ذلك قد يؤدي إلى تكرار عملية حساسة.

58. Repository Layer

كل مجموعة بيانات لها Repository مناسب.

مثلاً:

CustomerRepository CustomerNumberRepository ProtectionRepository ProtectionRequestRepository RenewalRepository NotificationRepository PackageRepository PaymentMethodRepository 

الـ UI لا يعرف تفاصيل Supabase.

59. ViewModel

الـ ViewModel مسؤول عن:

• حالة الشاشة.

• استقبال حدث المستخدم.

• استدعاء Use Case.

• تحويل النتيجة إلى UI State.

• منع التكرار.

• عرض Loading.

• عرض Success.

• عرض Error.

• مراقبة Local DB.

ولا يحتوي SQL.

60. Use Case

العمليات الوظيفية الرئيسية:

AddCustomerNumber CreateProtectionRequest CreateRenewalRequest ReadProtectionRequests ReadProtections ReadNumbers ReadNotifications MarkNotificationRead ChangePassword Logout 

61. العمليات التي تحتاج Trusted RPC

المرجع يحدد العمليات الحساسة على مستوى RPC/Trusted Operation، ومنها:

rpc_add_customer_number rpc_create_protection_request rpc_create_renewal_request 

ولا تعامل كـ INSERT عادي من الشاشة.

62. النتيجة الموحدة للعملية

كل عملية يجب أن تعيد نتيجة واضحة:

Success ValidationError Unauthorized Forbidden Conflict Duplicate NotFound Offline ServerError 

والـ UI يحولها إلى الحالة المناسبة.

63. القاعدة الذهبية

أي عملية:

UI Action 

لا تعتبر مكتملة إلا بعد:

Trusted Server Result 

ثم:

Local State Update 

ثم:

UI Update 

وليس:

UI Action → Local Fake Success 

64. التسلسل النهائي لتطبيق العميل

START ↓ AUTH ↓ RESTORE SESSION ↓ LOAD PROFILE ↓ CUSTOMER HOME ↓ LOCAL DB ↓ SYNC ↓ USER ACTION ↓ VIEWMODEL ↓ USE CASE ↓ REPOSITORY ↓ LOCAL READ / REMOTE WRITE ↓ RPC WHEN REQUIRED ↓ DATABASE TRANSACTION ↓ RESULT ↓ LOCAL DB UPDATE ↓ REACTIVE STATE ↓ UI

إضافة رقم → rpc_add_customer_number إنشاء طلب حماية → rpc_create_protection_request إنشاء طلب تجديد → rpc_create_renewal_request 

والعمليات الإدارية لا ينفذها العميل.

66. ما لا يقوم به تطبيق العميل

لا يقوم العميل مباشرة بـ:

• إنشاء حماية.

• قبول حماية.

• رفض طلب.

• تنفيذ مهمة تشغيلية.

• تعديل سعر.

• تعديل إعدادات الشركة.

• تعديل وسيلة دفع.

• تعديل حالة الدفع.

• إنشاء سجل مالي.

• تعديل Audit Log.

• تعديل تاريخ الحماية.
